## 0. 任務理解（Phase 0）

### 0.1 目標一句話

做一套 **Windows 上的「免切換中英混打」注音輸入法**：保留華碩智慧輸入法的打字手感（字母先上屏、藍色注音提示、聲調鍵轉換、Tab 接續），
但從**底層解碼演算法**重做，讓它能容錯（順序錯、多按、少按）、能學習個人習慣、選字時能在「中文 / 英文 / 原始按鍵」之間互換；
並整合**本地語音輸入**、**設定頁與詞庫管理**，未來擴充到其他輸入法（倉頡、拼音…）與 Vim 式編輯模式。

### 0.2 使用者回報的三個核心問題（以大千鍵盤還原）

| # | 現象 | 實際按鍵 | 應有結果 | 推測失敗原因 |
|---|------|----------|----------|--------------|
| 1 | `ㄨㄛˇ` 正常，`ㄛㄨˇ` 失敗 | `j i 3` vs `i j 3` | 兩者都應 → 我 | 以「嚴格順序」比對合法音節，不做重排 |
| 2a | 想打 `ㄟ` 卻變成 `o␣` | `o ␣` | 欸（ㄟ 一聲） | 單鍵＋空白被規則判為英文，無上下文評分 |
| 2b | 換順序打「更好」變 `/好` | `/ e 4 c l 3` | 更好（`ㄥㄍˋ`→`ㄍㄥˋ`） | `/` 被當符號留下，`e4`(ㄍˋ) 不合法被當贅字刪掉 |
| 2c | 專有名詞 `mvp` 變「勳」 | `m v p ␣` | mvp | `ㄩㄒㄣ`→`ㄒㄩㄣ` 合法就轉，沒考慮「勳」單字極罕用、mvp 是常見英文 |
| 3 | 不能建立常用字典／習慣鍵序 | — | 學習「這個人習慣 `ij3` 代表 我」 | 沒有可調的個人化輸入模型 |
| 選字 | 選字窗只能換同音中文 | — | 能把 `o␣` ↔ `欸`、`mvp` ↔ `勳` 互換 | 候選只來自單一解讀，沒有「多種解讀」的 N-best |

**共同根因（推測，華碩為閉源）**：決策是**局部、規則式、不可逆**的。每按一次聲調鍵就用規則判定「合法注音→轉；不合法→英文或刪除」，
沒有一個「全句、機率式、可回頭」的評分機制。所以只修規則（多加幾條例外）會越修越亂——這正是你說「需要從根本解決底層計算問題」的原因。
（值得注意：`mvp`→勳 代表華碩其實有做部分重排，但 `ㄛㄨˇ` 卻失敗，表示它的容錯是「特例清單」而非一般化模型。）

## 1. 華碩智慧輸入法拆解（調查對象）

### 1.1 官方功能

- 注音/英文混合模式（免按 Shift）、英文專用模式
- 自動完成：依習慣建議詞彙，按 `→` 或 `Tab` 帶入（帶入後呈底線可編輯）
- 標點符號選單：`` ` `` 或 `Ctrl+符號`
- 框選查詢：選字後按兩下 `Ctrl` 顯示翻譯與發音
- 刪除贅字（TypoCorrection）：按聲調時自動刪除誤觸鍵
- 自訂詞彙、快捷文字本（`` ` `` + Space 觸發）
- 支援 Win10/11 64-bit 20H2+，Microsoft Store 免費，1.1.0.0 起開放非華碩電腦

### 1.2 本機觀察到的架構（你電腦上的 v1.1.10.0，只看檔名與你自己的設定檔）

- **TSF 原生 C++ DLL**：`C:\Program Files\ASUS\AsusIME\zhtw\x64\AsusIME.dll`（profile 名稱「華碩注音」）
- **SQLite 詞庫**：`ZHTW_Dictionary_Base.db`（13 MB）、`English_Dictionary_Base.db`（23 MB）
- **個人學習庫**：`ZHTW_ / English_ / MIX_Dictionary_Customized.db`（已加密，無法匯出）——它有「混打」專屬的學習庫
- 設定程式為 .NET WPF；另有遙測元件（`AsusBusinessIntelligence*`）
- **沒有神經網路模型**：屬於「詞庫＋規則＋使用者頻率」的傳統設計
- 你的設定檔 `AsusIMEConfig.ini` 透露的開關：
  - `SpellingHintEnabled=1` → 即「旁邊顯示藍色注音」
  - `TypoCorrectionEnabled=1` → 刪除贅字
  - `AutoCompleteEnabled=1` → Tab 自動完成
  - `[DirectOutputMode]` → **依應用程式**切換「直接輸出模式」（Excel/Word/Notepad/Edge=1，Chrome/VS Code/LINE=0）
    表示它對不同 App 的相容性有個別處理，這是我們做相容性測試時要參考的清單。
  - `LeftShiftEnabled / RightShiftEnabled` → Shift 切換鍵可分左右

### 1.3 混合模式的手感（社群描述 + 你的描述）

1. 打字時**英文字母先直接顯示**在文字中
2. 可開啟「旁邊顯示注音」（藍色提示）讓你看到它目前的注音解讀
3. 按下聲調鍵時判定：合法 → 轉成中文；否則保留英文
4. 轉錯時：游標移到字前 → `↑` 叫出候選 → `←/→` 選 → `Enter`

### 1.4 社群回報的缺點（PTT IME 板、評測）

- 「容錯很小」、「相當考驗打字正確率」——與你的問題 1、2 一致
- 「有些字還是會判斷錯誤變英數字」、「有時無法自己選字」
- 「中英混合沒辦法自己決定開關」、「空白預設是中文全形」
- 系統負載重時偶爾無法正常打字、候選字故障

**結論：你的痛點不是個人問題，是這套設計的共通弱點。**

## 2. 市場調查：有沒有市場？誰需要？

### 2.1 使用人口

- 台灣中文輸入法使用者中，**注音及其變體佔七成以上**；嘸蝦米約 10.7%、倉頡約 9.9%（2011 市調，年輕世代受手機注音影響，注音比例應更高）
- 台灣日常書寫大量「中英夾雜」（晶晶體）：工程師、設計、行銷、學生、商務溝通（MVP、deadline、API、PR、meeting…）
- 最常見的痛：忘記切 Shift → 打出一串注音亂碼或英文亂碼，要刪掉重打

### 2.2 現有產品比較（Windows）

| 產品 | 價格 | 中英免切換 | 容錯/學習 | 開源 | 備註 |
|------|------|-----------|-----------|------|------|
| 微軟注音 | 免費 | 有「不合注音組合自動轉英數」選項，較陽春 | 普通 | 否 | 系統內建 |
| 新酷音 (PIME / chewing-windows) | 免費 | 無 | 選字智慧佳、有詞庫學習 | 是 (LGPL) | 2026 仍活躍 |
| 自然輸入法 V13 | 訂閱制 | 有智慧中英切換 | 佳 | 否 | 付費、使用者流失中 |
| **華碩智慧輸入法** | 免費 | **目前最順** | 容錯小 | 否 | 本專案的手感標竿 |
| RIME（小狼毫） | 免費 | 可設定但門檻高 | 可高度客製 | 是 | 適合進階玩家 |
| 小麥注音 | 免費 | 不做英文模式 | 佳 | 是 (MIT) | 主力 macOS |

**市場空缺**：Windows 上**沒有任何一款「開源 + 免切換中英混打 + 高容錯 + 可學習習慣」的注音輸入法**。華碩最接近，但閉源、容錯小、不可調。

### 2.3 語音輸入的市場訊號（很強）

- **Typeless**：2026 年在台灣爆紅，主打「中英夾雜、懂晶晶體」，Pro 方案 **US$30/月 或 US$144/年**，免費版每週 8,000 字
- **Wispr Flow**：同類訂閱制
- **Handy**（開源、MIT、3.2 萬星）：本地離線、免費，但不是輸入法、無法跟打字流程整合
- Windows 內建 `Win+H`：引擎老舊、中英混說辨識差（你先前的調查結論）

→ 有人**願意每月付費**買「繁中 + 中英混說」的語音輸入。我們能提供「**本地、免費、跟輸入法整合、用你自己的詞庫做熱詞**」的版本，是明確的差異化。

### 2.4 「各國通用」的可能性

「自動判斷鍵盤序列屬於哪種語言」是被驗證過的需求類別：
- 俄語圈的 **Punto Switcher**（俄文/英文鍵盤自動校正）有大量使用者
- 韓文的「한/영」切換錯誤也是同樣痛點（`dkssud` → 안녕）

可擴充性評估：

| 方向 | 難度 | 理由 |
|------|------|------|
| 注音 + 英文 | ★★☆ | 有聲調鍵當天然分隔，最容易做好 → **首發** |
| 漢語拼音 + 英文 | ★★★ | 無聲調、拼音本身就是拉丁字母，衝突多；可共用中文詞庫 |
| 韓文 2-set + 英文 | ★★☆ | 字母結構規則明確，類似注音 |
| **倉頡 + 英文** | ★★★★ | 倉頡碼就是 a–y 字母、1–5 碼都可能合法，與英文單字大量重疊，又沒有聲調分隔 → 需要很強的語言模型，屬研究級 |
| 日文羅馬字 + 英文 | ★★★★ | 羅馬字與英文高度重疊 |
| 嘸蝦米 | 法律風險 | 字根表為行易公司專有，只能做「使用者自備字根表」模式（PIME 的 cheliu 即如此） |

**建議**：引擎從第一天就設計成「輸入方案外掛化」（layout/scheme plugin），但首發只做「注音（大千）+ 英文」做到極致。

### 2.5 市場結論（老實說）

- **對你個人：值得做**。痛點明確、你每天在用、市面沒有直接解。
- **對推廣：是「小眾但真實」的市場**。輸入法很難直接收費（免費替代品多，華碩背後有大公司），
  較可能的價值來源：開源聲譽／作品集、語音輸入（已證實有付費意願）、重視隱私的企業／個人。
- **策略**：先做「自己每天離不開」的版本，架構按「可散布」標準設計（乾淨授權、可打包、可簽章），等手感穩定再決定是否推廣與商業模式。

## 3. 技術選型

### 3.1 Windows 輸入法前端：四種做法

| 方案 | 做法 | 優點 | 缺點 |
|------|------|------|------|
| **A. PIME + 自訂 Python 後端**（建議） | 用 PIME 的 C++ TSF DLL 當前端，我們寫 Python 後端 | 真正的系統輸入法（Win+Space 切換、所有 App 可用）；前端已在社群驗證多年；我們專注引擎；Python 可行 | 候選窗/提示窗外觀受 PIME 限制（可改 C++ 原始碼）；安裝需一次性系統管理員權限 |
| B. 自寫 TSF DLL（C++/Rust） | 從零實作 TSF COM | 完全掌控 UI | 工程量大、COM/TSF 坑多，與核心價值（演算法）無關 |
| C. 全域鍵盤 Hook + 浮動視窗（純 Python） | 攔截按鍵、SendInput 送字 | 最快做出原型 | 不是真輸入法：組字無法 inline、游標位置抓不準、管理員權限程式/遊戲/密碼欄失效、易被防毒當 keylogger |
| D. 基於 RIME（小狼毫） | 寫 RIME schema + Lua | 拼寫運算(algebra)可做部分容錯 | 不是 Python；RIME 的架構難以實現我們要的全句機率式中英判斷 |

**PIME 現況（已查證）**：
- GitHub `EasyIME/PIME`，2026-07 仍有提交，已加入 SignPath 程式碼簽章、Launcher 改寫為 Rust、主線內建 Python 3.12
- 最新正式版仍是 **1.3.0-stable（2023-01）**，內建 Python 3.8
- **你的電腦已安裝 PIME 1.3.0**（目前只有新酷音一個輸入法）
- 通訊協定很單純：Launcher ↔ 後端行程走 **stdin/stdout，每行一個 JSON**；`backends.json` 可宣告任意後端
- → 我們可以**新增自己的後端**，指向我們自己的 Python 3.12 環境，不受 PIME 內建 3.8 的限制，崩潰也不會影響新酷音

**提醒**：
1. 1.3.0 的後端路徑是相對於 `C:\Program Files (x86)\PIME`，需在那裡建立一個 junction 指向我們的部署資料夾（建議用純英文路徑，避開專案路徑中的中文字）
2. 新增輸入法需要重新註冊 PIME 的 DLL（一次性、需系統管理員）
3. 候選窗與提示樣式若要做到華碩的藍色注音提示，MVP 先用 PIME 現成的 UI 元件（候選窗／提示訊息）模擬；要 100% 還原可能需要改 PIME 的 C++ 前端（你電腦有 VS 2022）

### 3.2 為什麼 Python 可以（以及界線）

- 每按一鍵要在 ~10–20 ms 內算完。組字緩衝區通常 < 50 鍵，lattice 規模約數百個節點，Python 可以應付
- 引擎**只用標準函式庫**（`sqlite3`, `json`…），好測試、好移植
- 語音輸入是**獨立行程**（有自己的 venv，可裝 PyTorch / CTranslate2 / sherpa-onnx），不拖慢打字
- 若日後效能不足：把解碼器熱點用 Rust（PyO3）重寫，API 不變。引擎與前端以「純資料」介面溝通，未來要搬到 Rust/行動裝置也可行

## 4. 核心演算法設計：從根本解決

### 4.1 把打字當成「雜訊通道」問題

使用者心中想的是文字 **T**（中文詞 + 英文詞的混合），手指打出的是按鍵序列 **K**（有順序錯、多按、少按）。
我們要找：

```
T* = argmax  P(T) × P(K | T)
       T
```

- **P(T) 語言模型**：中文詞頻（unigram → 之後 bigram）、英文詞頻、技術詞彙表、**中英切換成本**、**個人使用紀錄**（近期/常用加權）
- **P(K | T) 打字模型**：一個音節可以被打成：
  - 完全正確（最高分）
  - **同音節內順序錯**（`ㄛㄨˇ`→`ㄨㄛˇ`；注音每類最多一個符號：聲母/介音/韻母/聲調，所以重排結果唯一）→ 問題 1
  - 多按一鍵（贅字）、少按一鍵、按到相鄰鍵、聲調鍵相鄰誤觸（3/4、6/7）→ 問題 2
  - 每種錯誤有「成本」，且**成本會依你的習慣學習**（你常 `ij3` → 這個重排對你幾乎免費）→ 問題 3
- **解碼**：對整個未送出的緩衝區建 lattice，用 Viterbi/beam search 找最佳解，**同時保留 N-best**

### 4.2 每個問題怎麼被解決

| 問題 | 新做法 |
|------|--------|
| `ㄛㄨˇ` 失敗 | 重排是打字模型中的一種低成本錯誤，自動轉正為 `ㄨㄛˇ` |
| `o␣` 變英文 | `o` 作為英文單字的機率極低、`欸` 在中文上下文中機率高 → 中文勝出；若真要英文 o，候選窗可一鍵換回 |
| `/e4cl3` → `/好` | `/ e 4` 視為一個音節的重排 → `ㄍㄥˋ` 更；不再有「殘留斜線」或「默默吃掉字」 |
| `mvp` → 勳 | 英文/技術詞表中 `mvp` 機率高；「勳」單字罕用 → 保留 mvp；你的選擇會被學習 |
| 選字不能跨解讀 | 候選窗列出**跨類別候選**：`欸 / o / ㄟ（原注音）`、`mvp / MVP / 勳 / 熏`… |
| 前面判錯後面救不回 | 整個緩衝區每鍵重新解碼，後文可以修正前文（像新注音），而不是一按聲調就定案 |
| 去除雜訊 | 不再「刪鍵」，而是把多餘鍵當成有成本的錯誤；只有在修正後的解讀**明顯更合理**時才採用，而且可還原 |

### 4.3 個人化學習（問題 3）

1. **個人詞庫**：你選過的詞提高權重（含中英混合詞，如「開 meeting」）
2. **按鍵習慣表**：記錄「原始按鍵 → 你最後選的結果」，例如 `ij3` → 我，下次直接命中
3. **錯誤模式統計**：你常犯哪種錯（哪兩鍵常顛倒、哪個鍵常多按）→ 動態調整打字模型成本
4. 全部**存在本機**，可在設定頁檢視、編輯、匯出、清除

### 4.4 怎麼證明它比較好：評測基準

- 用大量中英混合句子 → 轉成「理想按鍵」→ 依真實比例注入錯誤（重排、多按、相鄰鍵）→ 解碼 → 量測：
  - 中文字正確率、英文 token 保留率、**誤轉率**（把英文誤轉中文、或反之）
- 你回報的每個 case（`ij3`、`o␣`、`/e4cl3`、`mvp`…）都會變成**回歸測試**
- 每鍵延遲量測（目標 < 15 ms）

## 5. 語音輸入（Phase 6）

> 你計畫中寫的是「tts」，但從你附的調查內容看，需求是 **STT（語音轉文字）輸入**。下面以 STT 規劃；若也想要 TTS（例如框選朗讀），請另外確認。

### 5.1 模型比較（2026 現況）

| 模型 | 授權 | 特色 | 適合 |
|------|------|------|------|
| **Breeze-ASR-25**（聯發科創新基地） | Apache-2.0 | Whisper-large-v2 微調，**專為台灣華語與中英夾雜**優化，code-switching 比原版 Whisper 提升約 56% | **你的 RTX 4070（12 GB）可流暢跑** → 首選 |
| SenseVoice-Small（阿里） | 程式 MIT／模型 FunASR Model License | 非自回歸，比 Whisper-large 快約 15 倍，純 CPU 可跑；輸出偏簡體需 OpenCC 轉繁 | 無 GPU 的使用者、低延遲備案 |
| Qwen3-ASR 0.6B / 1.7B（2026-01） | Apache-2.0 | 華語 benchmark 目前最強之一，52 語言 | 值得實測比較；runtime 較重 |
| Breeze-ASR-26 | Apache-2.0 | **台語（Taigi）語音 → 華語文字** | 未來「說台語打中文」的彩蛋功能 |

**你的硬體**：i9-14900K、128 GB RAM、RTX 4070 12 GB → 所有方案都跑得動，可以同時保留 GPU 主力 + CPU 備案。

### 5.2 設計

- 獨立常駐行程（系統匣圖示），全域熱鍵：**按住說話、放開送出**（也支援切換模式）
- 預錄緩衝（按下前 ~500 ms 也收音，避免第一個字被切掉）、VAD 去靜音
- **用你輸入法的個人詞庫當熱詞**（Whisper `hotwords`/prompt）→ 你的專有名詞、人名更準，這是 Handy/Typeless 做不到的整合點
- OpenCC `s2twp` 轉台灣用語、標點處理
- 以 Unicode `SendInput` 送到游標位置（不汙染剪貼簿），長文字用剪貼簿貼上備援
- 可選：後處理去贅詞（「呃、那個」）、口語轉書面（本地或 API，後期再議）

## 6. Vim 式編輯模式（Phase 8 構想）

輸入法的「組字緩衝區」本身就是一個小編輯器，非常適合模式化操作：

- **輸入模式**（預設）：正常打字
- **選字/編輯模式**（例如按 `Tab` 或 `` ` `` 進入）：
  - `h / l`：在詞段間移動；`j / k`：切換該段候選
  - `e`：該段在 **中文 ↔ 英文 ↔ 原始按鍵** 之間切換（直接解決 `o`↔`ㄟ`）
  - `x`：刪除該段；`s`：重新解碼該段；`u`：復原上一個自動修正
  - 數字鍵：直接選第 N 個候選；`.`：重複上一個修正動作
- 好處：手不用離開主鍵區，就能修正任何判錯，而且**每次修正都是學習訊號**

### 7.1 主要風險

1. **詞庫/語言模型品質**才是最大工程（不是 TSF 管線）。華碩有團隊；我們靠開源資料 + 個人學習 + 評測基準持續調整
2. 輸入法相容性：部分 App（遊戲、以系統管理員執行的程式、某些 Electron App）行為特殊，需逐一測試
3. Python 延遲：需剖析，必要時把熱點改 Rust
4. 散布：需要安裝程式、DLL 簽章（PIME 的 SignPath 免費簽章僅限開源專案）、授權整理
